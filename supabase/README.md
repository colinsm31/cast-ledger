# Supabase backend

The AceStock database: Postgres (via Supabase) with row-level security, calculated
stock and balance views, and server functions (RPCs) that move all money and stock in
single transactions. The web app and the planned iOS app both talk to it directly.

## Layout

| Path | Purpose |
|------|---------|
| `functions/create-staff/` | Edge Function: admins create staff accounts (public sign-up is off). Deploy with `supabase functions deploy create-staff`. |
| `migrations/` | Numbered, re-runnable schema migrations. `0001`–`0007` are the original precast schema; `0008` converted it to retail, and everything after builds AceStock. |
| `tests/` | pgTAP database tests, run with `supabase test db`. `tests/helpers/setup.psql` holds shared fixtures. |
| `seed/tennis_seed.sql` | Sample tennis-shop catalog. Loaded automatically by `supabase start` / `supabase db reset` (see `[db.seed]` in `config.toml`). |
| `seed/advantageserver_*.sql` | One-time import of a shop's AdvantageServer inventory export. |
| `seed/reset_all_data.sql` | Clears shop data in a test project. **Never run against production.** |
| `apply_all.sql` | Every migration concatenated, for pasting into a brand-new project's SQL editor. Generated by `scripts/build-apply-all.sh`; don't edit by hand. |
| `config.toml` | Supabase CLI settings for the local stack. |

## Local development and tests

Requires Docker. The CLI can run through npx (no global install needed):

```bash
npx supabase@2.118.0 start -x studio,imgproxy,mailpit,realtime,storage-api,edge-runtime,logflare,vector,supavisor,postgres-meta
npx supabase@2.118.0 test db
```

`start` boots Postgres, Auth and the API, applies every migration and loads the sample
seed. `test db` runs every file in `tests/`. After changing a migration, rebuild the
database with `npx supabase@2.118.0 db reset` before re-running the tests.

`../scripts/test-concurrency.sh` checks what pgTAP can't: two connections racing for
the same gift card, store credit, sale line, string job or last unit in stock. It
creates and removes its own rows; run it against the local stack only.

The same tests and the concurrency checks run in CI
(`.github/workflows/database-tests.yml`) on every push and pull request.

## Writing a migration

- Name it `NNNN_short_description.sql` with the next number, and start with the
  header comment block used by the existing migrations: what changes and why.
- Make it **re-runnable**: `if not exists`, `create or replace`, `drop … if exists`
  before re-creating constraints and policies.
- Redefining a server function means copying its latest version in full. Search
  `migrations/` for the newest `create or replace function <name>`.
- Add or update tests in `tests/` for any behavior change.
- Regenerate the paste-in file: `./scripts/build-apply-all.sh`.

Applying migrations to the hosted test and production projects is covered in
[`../ENVIRONMENTS.md`](../ENVIRONMENTS.md).

## Conventions

- snake_case, plural table names, `id uuid` primary keys (client-generatable).
- **Histories are append-only**: `inventory_txns`, `gift_card_txns`,
  `store_credit_txns`. Corrections are new rows, never edits.
- **Balances are calculated, never stored**: stock (`product_stock`,
  `product_available`), gift cards (`gift_card_balance`), store credit
  (`customer_store_credit`).
- **Money and stock move through server functions** (`record_sale`,
  `record_refund`, `receive_stock`, `adjust_stock`, `receive_units`,
  `advance_string_job`, …) so every check runs in one transaction. Clients
  can only *read* the money and stock tables; these functions are
  `SECURITY DEFINER` so they can write them. A new function that writes those
  tables must be `security definer` too.
- **Every function pins `search_path = public, pg_temp`** and is executable by
  `authenticated` only (never `anon`); trigger functions aren't executable at all.
- **Views use `security_invoker = true`**, so they apply the reader's
  row-level security. A view without it would bypass RLS for everyone.
- **Signed-out users (`anon`) have no access** to tables, views or functions.
  The app requires sign-in for everything.
- **Only approved staff have access.** Accounts start as `pending`. Row-level
  policies use `is_staff()` (never plain `true`), and a statement-level trigger
  (`trg_enforce_staff_writer`) on every table refuses writes by a signed-in
  account that isn't staff, including writes inside server functions. **A new
  table needs a `using (is_staff())` policy and the same trigger.**
- **Admin-only configuration** (settings, categories, attribute definitions) is
  writable only when `is_admin()` is true; staff can read it.
- **Attribution**: money and stock records carry the signed-in staff member
  (`user_id` / `*_by` columns default to `auth.uid()` and reference `profiles`).
